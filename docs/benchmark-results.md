# モデル拡張の独立検証（2026-11-14）

ユーザーの「まず、検証して」に基づき、ゲーム本体を変更せず、`tools/benchmark/`に独立した試作を作って測定した。本・バインダーの実装再開を意味しない。

## 実測結果

Windows、Intel Core i7-1185G7、Chrome 157、CPUのみのJavaScript。Web Worker内で動作。アニメーションなし、GPU・KVキャッシュ・量子化なし。

| 項目 | 候補A | 候補B |
| --- | ---: | ---: |
| 文脈長（トークン） | 128 | 256 |
| 1トークンの表現の成分数 | 48 | 96 |
| 層／ヘッド | 3／3 | 3／3 |
| 語彙容量 | 1,024 | 2,048 |
| 学習するパラメータ数 | 160,768 | 641,024 |
| 設定・トークナイザー込みの保存容量 | 649,229 bytes（約0.65 MB） | 2,570,262 bytes（約2.57 MB） |
| 短い20往復を12周学習（240更新） | 3.58秒 | 15.67秒 |
| 文脈満杯で1回推論（5回の中央値） | 61.5 ms | 618.0 ms |
| 文脈満杯で1回学習（5回の中央値） | 152.7 ms | 1,370.2 ms |
| 文脈満杯から30トークン生成（3回の中央値） | 1.83秒 | 17.61秒 |

学習例は日本語の短い会話。BPE後の各系列は6〜21トークンであり、128／256トークンの長文を240回学習した時間ではない。学習240更新は各構成で1回の通し測定。フル文脈試験は合成列による負荷測定で、30トークンは30文字とは限らない。

実際に作った語彙は特殊トークン込み358個、BPE結合規則100個。両構成で同じ語彙を使い、出力計算自体は容量1024／2048の全欄を使用した。大きい語彙を十分な文章で学習したときの品質は今回検証していない。

## 正しさの確認

- 全22パラメータ群から計66要素を有限差分で検算。最大相対誤差は約5.78×10⁻⁹。
- 後ろのトークンを変更しても、それ以前の位置の出力が変わらないことを確認。
- 微小モデルの100更新で損失2.537→0.977。候補Aの会話例で6.961→4.809、候補Bで7.642→4.670。学習による損失低下を確認したが、会話の成立を保証する指標ではない。
- 「りんご」「遊ぼう」「鳴くよ。」等が複数文字のトークンになった。学習例にない漢字や絵文字もUTF-8バイトを使って往復可能。
- 両構成とも、Float32重み・設定・BPE情報を保存して再読込した後、予測確率が完全一致。

## 判断と残る課題

このPCでは候補Aを実装の出発点にできる見通しが立った。モデルをファイルで交換できる容量も確保できる。ただしゲームの交換画面や、安全な外部ファイル読込は未実装。

スキップでアニメーションの待ち時間は省けるが、上記の数値計算時間は残る。数値計算を表示から分離し、通常表示／スキップで同じ更新結果になる設計にする。候補Bはファイル容量よりも、長い文脈での返答時間が課題。必要なら最後の位置だけの出力計算、KVキャッシュ等を別途検証する。

今回の試作は全位置・全層を計算し、系列単位で損失を平均してSGD更新する。現ゲームの1位置ごとの更新とは異なる。中間値はFloat64、推論にも学習用領域を確保する未最適化版なので、速度の最適値ではない。ゲームの描画を併走した時間、スマートフォン実機、長時間のメモリ、生成文章の品質は未測定。

測定後の合意で、候補Aを新規作成の初期値とし、詳しい設定から検証済み構成を選ぶ方針になった。[構成設定の仕様](model-settings.md)を参照。初期値以外の選択肢の確定とゲーム統合は未実施。ゲーム本体の実装は引き続き停止中。
